# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Three static, zero-build web apps (PWAs) sharing one repo, deployed on Netlify. No
framework, no bundler, no `package.json` — each app is hand-written HTML with an inline
or sibling `<script>`. UI text and code comments are in Italian; keep that convention.

1. **Daycation** (`index.html` + `data.json`) — finds same-day round trips by plane from
   Bologna (BLQ): leave in the morning, come back the same evening.
2. **Weekend** (`weekend.html` + `weekend-data.json`) — finds 1–3 night getaways (Fri/Sat
   out, Sunday back), computing real hours at the destination.
3. **Pronostici** (`pronostici/`) — a value-betting tool (football + tennis) using The Odds
   API. Fully independent app with its own `app.js`, `style.css`, and service worker.
4. **PDF → Markdown** (`pdf2md/index.html`) — a fully client-side converter: extracts text
   with PDF.js (CDN-loaded library; the file is never uploaded) and applies heuristics
   (heading size, bullet symbols) to emit Markdown. Pages with no embedded text (scanned
   PDFs) are rendered to a canvas and read via **OCR** with Tesseract.js (`ita+eng`,
   lazy-loaded from CDN only when the OCR option is enabled).

All four apps cross-link via a shared `.prod-switch` header nav (✈️ In giornata · 🧳 Weekend ·
⚽ Pronostici · 📄 PDF→MD). Root apps use bare paths (`weekend.html`, `pronostici/`, `pdf2md/`);
the subfolder apps use `../`. There is no shared CSS — each app restyles `.prod-switch` in its
own palette, so keep the four navs in sync by hand when adding/renaming an app.

Daycation and Weekend are cross-linked via a header product switcher (`✈️ In giornata` /
`🧳 Weekend`) and both consume datasets generated by the same parser.

## Commands

```bash
# Serve any app locally (no build step exists)
python3 -m http.server 8080         # from repo root → http://localhost:8080
python3 -m http.server 8080         # from pronostici/ for the betting app

# Regenerate flight datasets (writes data.json AND weekend-data.json at repo root)
python3 parse_blq.py                # requires poppler-utils (pdftotext) on PATH
```

There are no tests, linters, or a build command. The CI "build" is literally `echo`.

## How flight data flows (the core architecture)

`parse_blq.py` is the only backend. It is run nightly by GitHub Actions, **not** at request
time — the apps just `fetch()` static JSON.

1. `detect_current_season()` derives `summer_YYYY` or `winter_YYYY_YYYY+1` from today's date
   using DST boundaries (last Sunday of March/October), then downloads
   `bologna-airport.it/System/pdf/orario_voli_<season>.pdf`, with a fallback to the other
   season if that URL 404s.
2. `pdftotext -layout` → text; a single regex (`RE_FLIGHT`) parses each flight row
   (destination, airline, flight no, dep/arr time, a 7-char weekday frequency string, and
   validity date ranges). Validity ranges can appear inline OR on their own lines
   (`RE_VAL`), which is why `parse_section` does a second pass to attach orphan date ranges
   to the preceding/following flight.
3. The departures/arrivals split in the PDF is found heuristically by
   `find_departures_arrivals_split` (looks for "Arrivi voli di linea" / "Flight arrivals").
4. Two outputs are written:
   - **`data.json`** (Daycation): filtered to departures 04:00–14:00 and arrivals ≥16:00,
     intersected so only cities with a viable same-day round trip remain.
   - **`weekend-data.json`** (Weekend): the *unfiltered* timetable (all cities with any A/R),
     because weekends need early-morning and late-evening flights that Daycation discards.

**Compact JSON format** (both files): top-level `{meta, d, a}` where `d`=departures,
`a`=arrivals. Each flight is a positional array, not an object:

```
[city, flightNo, dep("HH:MM"), arr("HH:MM"), freqBitmap(int), [[startMD, endMD], ...]]
```

- `freqBitmap` is a 7-bit int: bit `(weekday-1)` set means the flight runs that day, where
  weekday 1=Monday…7=Sunday. Frontend checks it with `freqOk(bm, wd) = (bm >> (wd-1)) & 1`.
- Validity ranges are `["MMDD","MMDD"]` strings; a date matches if `start <= MMDD <= end`.

If the airport changes the PDF layout or URL scheme, the regex/heuristics break and the
nightly Action fails loudly — fixing the parser is the expected maintenance task.

## Frontend conventions (Daycation & Weekend)

- All logic lives inline in the single `.html` file. Shared idioms: `t2m` (HH:MM→minutes),
  `freqOk`, `inVal`, ISO date helpers, and the weekday convention `Sunday=7` (`isoWd`).
- **`AIRLINES`** and **`CITY_INFO`** are large hardcoded maps (flight-code prefix → name/color;
  city → IATA/flag/description). New routes appear automatically from the data, but show a
  generic 🌍 placeholder until added to `CITY_INFO`. Update these maps when adding cities.
- **`XSCHENGEN`** is a hardcoded set of extra-Schengen cities; `haircutMin` subtracts more
  airport-overhead time (140 vs 100 min) when computing usable hours at destination.
- `bestComboForCity` is the matching engine: it pairs every valid outbound with every valid
  return for a date, subtracts the haircut, and keeps the best combo over `minH` hours.
- Prices are never stored. "Cerca prezzi" builds a Skyscanner deep link (`skyLink`) filtered
  to the route/date.
- Daycation logs anonymous usage to `localStorage` (`dcb_stats_v1`) via `track()`; there is
  no server/analytics backend.

## Frontend conventions (Pronostici)

- All logic is in `pronostici/app.js`; state persists to `localStorage` (`STORE_KEY`). No
  account, no server — backups are manual JSON export/import.
- Core math: `noVig()` strips bookmaker margin; consensus probability is the mean of
  no-vig probabilities across **all** bookmakers; `valueOf()` computes edge + Kelly fraction;
  `stakeFor()` applies the user's Kelly fraction (default ¼) to the bankroll.
- Live odds come from The Odds API (`ODDS_BASE = https://api.the-odds-api.com/v4`,
  `regions=eu&markets=h2h`). The API key is user-supplied (free tier) and stored only in
  `localStorage` — never commit a key.
- "Link magico": `#key=...` or `?key=...` in the URL is captured, saved, and stripped from
  the address bar so the key can be shared into the app via a link.

## Service workers & caching

Both `sw.js` (root) and `pronostici/sw.js` use **network-first for HTML and `*data.json`**
(so edits go live immediately) and **cache-first for icons/images/manifests**. When you ship
breaking changes to cached assets, bump the cache version constant (`CACHE = 'dcb-v5'` in
root `sw.js`) to force clients to drop stale caches.

## Deployment

- GitHub Actions (`.github/workflows/update-data.yml`) runs the parser nightly at 04:00 UTC
  (and on manual `workflow_dispatch`), committing `data.json` + `weekend-data.json` only if
  they changed. Requires the repo's Actions setting to be **Read and write permissions**.
- Netlify auto-deploys on push; there is no build (command is `echo`).
- **Gotcha:** `netlify.toml` and `README.md` reference a `public/` publish directory, but no
  `public/` folder exists — the apps actually live at the repo root. Treat the repo root as
  the served directory; don't move files into a `public/` dir without updating Netlify config.

## Conventions to preserve

- Keep apps dependency-free and build-free; don't introduce npm/bundlers casually.
- Keep the compact positional JSON format and the parser/frontend in sync — both sides know
  the array index meaning by position.
- UI strings and comments stay in Italian.
